# Edge function rules
- PipeRun sync hydrates person contacts via a read-only persons/{id} GET, matches leads by phone when e-mail is missing, and keeps deals without contacts keyed by piperun_id; deals typed directly in PipeRun otherwise never reach the system.
- PipeRun person/company contacts are written and read only through the shared `piperunGet/Post/Put` helpers, which translate to `contact_emails`/`contact_phones`, request `with[]=contactEmails,contactPhones`, merge existing contacts on PUT and use `?email=`/`?phone=` list filters; the legacy `emails[]`/`phones[]` keys and filters are silently ignored by PipeRun and left persons without e-mail and caused duplicate persons.
- PipeRun sync hydrates company contacts separately and does not skip unchanged deals when missing contacts become available; company identifiers must never merge distinct people.
- PipeRun deal sync writes `telefone_normalized` alongside `telefone_raw` using the shared Brazilian phone normalizer; lead cards, search and phone matching read only the normalized phone.
- Sentinela daily e-mail report (sentinela-email-report, cron 03:00 UTC) classifies groups by name/links into internal, client, nurturing and external and identifies senders via team/lead WhatsApp LID or phone; the recipient is fixed server-side because the endpoint is called unauthenticated.
- WhatsApp Cloud API numbers connected through Zernio deliver inbox events to the signed `zernio-whatsapp-inbox` endpoint, which only ingests into whatsapp_inbox (dedup by wamid, lead by normalized phone); it sends nothing, so Evolution/WaLeads automations stay unchanged.
- Blueprint meetings: `blueprint-meeting-scheduler` (service/staff only) is triggered fire-and-forget by smart-ops-piperun-webhook when a Vendas deal enters Apresentação/Visita (99295) or any activity is created in Vendas; an open Reunião-type activity (54384) with date moves early-stage deals (Sem contato/C1/C2/C3/SDR) forward to 99295 (user-authorized Golden Rule exception, never backwards, never won/lost), advanced stages only get Meet/note; entering 99295 without a meeting creates one `[Blueprint]` task asking the seller to schedule (system activities never count as meetings). One lead_activity_log row (`reuniao_agendada`, dedupe_hash `meet:<deal>`) is lock and per-step state; Calendar id `sdmeet<deal>` keeps Meet idempotent; times are never invented; only field 800593, stage_id on the move, one prep note and one task are written.
- Blueprint post-meeting: `blueprint-meeting-analyzer` (15-min cron; no-arg sweep is public, idempotent and returns counts only; deal_id/force need service/staff) reads Gemini notes only from the calendar event attachments or docs in the organizer's Meet Recordings folder whose name starts with the event title — never by time proximity — trying GOOGLE_DRIVE_API_KEY_1 then GOOGLE_DRIVE_API_KEY; analysis is stored on `reuniao_analisada` (dedupe meetanalysis:<deal>) plus one PipeRun note, with observable commercial profile only.
- Cognitive analysis (`cognitive-lead-analysis`) uses LIA chat plus the lead's meaningful timeline interactions (fixed signal list shared with the `trg_dispatch_cognitive_on_timeline` trigger on lead_activity_log; snapshots/sync noise excluded). Each new signal dispatches it immediately via pg_net (throttled 15s per lead in cognitive_dispatch_state, function waits 20s in background and compares against `_audit.signals_until`), with `trigger: "timeline"` writing a PipeRun note only on stage change; no cron sweep for timeline signals, the card refreshes from lia_attendances realtime.
- lia-assign main `new_deal` path clears the lead's inherited piperun_id when PipeRun shows no open Vendas/Estagnados/CS deal (and the deals fetch succeeded), so the cached-deal validator, Golden Rule gate and create lock decide; keeping an inherited closed/CS id silently skipped deal creation for returning clients.
- Evolution GO `/group/create` receives participants as full `55DDDNUMBER@s.whatsapp.net` JIDs; bare digits make WhatsApp drop the request ("info query timed out") and no group is created.
- Manual blasts of a social post call `wa-post-teaser` (internal staff only) first: AI teaser of max ~3 lines without prices plus the post link, and the cover image copied to `wa-media` because Instagram CDN URLs expire; the full caption is never sent to groups.
- Campaign social nodes (post_ig/post_yt/link_ig/link_yt) get their AI summary in the editor via `wa-post-teaser` style `resumo` (same prompt as auto-blast, `_shared/post-summary.ts`) and store it as `resumo` beside the original caption; wa-dispatcher never calls an LLM and sends media (media_urls → media_url → thumbnail_url, type by extension) with the summary capped at 1,024 chars, falling back to text only when no image exists or the provider rejects it without timeout, so the per-minute send path stays fast and never duplicates.
- Post Grupos auto-blast follows the screen: active instance + groups selected in it + networks, and a target only receives when its wa_groups row is still owned by that same instance and enabled; admin is not required because audience groups accept posts from any participant (`_shared/post-group-eligibility.ts`, mirrored in `src/lib/postGroupStatus.ts`; wa-group-blast filters enabled only). Group sync never lets a non-admin number take over a group row owned by another admin number, and `wa_group_instance_pin` + `trg_pin_group_instance` force pinned groups' instance_name, because wa_groups has one row per JID and dispatch uses its owner (see `_shared/README.md`).
- Agenda "Tabela vigente" is chosen server-side in `crm-insercao` (`price-table.ts`): active tables flagged `commercial_active` with full dates, valid 00:00 start to 23:59 end in São Paulo, latest start wins overlaps; the PDF snapshot reuses `kol_pdf_url`, published on save, so phone-logged team members never read promotional tables or run the PDF builder against RLS.
- Promotional table creatives: `promo-creatives` (admin only) creates one Drive folder per table under the campaign parent folder, uploads files there plus a `wa-media` copy, and generates/stores each creative's default WhatsApp template (`whatsapp_message`, AI body + fixed footer with `{cupom}`/`{validade_cupom}`/`{vendedor}`); the Agenda `crm-insercao` `creatives` action only fills that template with the server-resolved seller's coupon via `_shared/creative-message.ts` (no AI for sellers; a seller's own edit is stored per team member in `promotional_creative_seller_messages` through `creative_save_message`/`creative_reset_message`), so codes and dates stay exact and the message is defined once in the editor.
- Promotional table social posts: `promotional_tables.social_hashtags` (normalized, exact-tag match in `_shared/promo-social.ts`) selects published Instagram `social_posts`; each post's default WhatsApp template (Post Grupos summary prompt from `_shared/post-summary.ts` + post link + the creatives coupon footer) is generated once per table/post into `promotional_social_post_messages` (editor via `promo-creatives`, or lazily on Agenda open, bounded per request, never overwriting editor edits) and rendered per seller in `crm-insercao` `social_posts`, with seller edits in `promotional_social_seller_messages`; one template per post keeps sellers' AI cost and text consistent.
- Commercial campaign forms are `sdr_captacao` forms flagged `smartops_forms.is_commercial_campaign` (legacy: name prefix `# - CAMPANHA COMERCIAL -`; same standard flow), so renaming never turns off buttons, group redirect or exact-name origin; lia-capture asks the form's capture buttons after identity and before ingest, validates the choice server-side, sends it as the CRM product of interest with the exact form name as origin, and auto-opens the success_redirect_url group; keeps campaign CRM routing identical to SDR forms.
- Commercial campaign forms link their promotional table via `smartops_forms.promotional_table_id`; lia-capture uses the linked table name as campaign display name and stores the link on the interest timeline entry, so the table remains the single campaign identity.
