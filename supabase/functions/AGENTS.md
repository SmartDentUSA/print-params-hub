# Edge function rules
- PipeRun sync hydrates person contacts via a read-only persons/{id} GET, matches leads by phone when e-mail is missing, and keeps deals without contacts keyed by piperun_id; deals typed directly in PipeRun otherwise never reach the system.
- PipeRun person/company contacts are written and read only through the shared `piperunGet/Post/Put` helpers, which translate to `contact_emails`/`contact_phones`, request `with[]=contactEmails,contactPhones`, merge existing contacts on PUT and use `?email=`/`?phone=` list filters; the legacy `emails[]`/`phones[]` keys and filters are silently ignored by PipeRun and left persons without e-mail and caused duplicate persons.
- PipeRun sync hydrates company contacts separately and does not skip unchanged deals when missing contacts become available; company identifiers must never merge distinct people.
- PipeRun deal sync writes `telefone_normalized` alongside `telefone_raw` using the shared Brazilian phone normalizer; lead cards, search and phone matching read only the normalized phone.
- WhatsApp Cloud API numbers connected through Zernio deliver inbox events to the signed `zernio-whatsapp-inbox` endpoint, which only ingests into whatsapp_inbox (dedup by wamid, lead by normalized phone) and sends nothing, so Evolution/WaLeads automations stay unchanged; quick-reply button clicks (`metadata.buttonPayload`) are answered separately by `zernio-wa-button-reply`, dispatched by the `trg_dispatch_wa_button_reply` trigger on whatsapp_inbox.
- Blueprint rules live in supabase/functions/blueprint-meeting-scheduler/AGENTS.md and supabase/functions/blueprint-meeting-analyzer/AGENTS.md.
- Rules for `crm-insercao` (Tabela vigente), `promo-creatives` (creatives and social posts), `lead-dossier` and `catalog-images-localize` live in the AGENTS.md of each of those function directories.
- Rules for `zernio-wa-broadcast` (including WhatsApp Oficial history), `zernio-wa-button-reply`, `wa-dispatcher`, `wa-post-teaser` (Post Grupos and campaign social nodes), `smart-ops-send-gmail`, `smart-ops-email-scheduler-tick`, `smart-ops-ingest-lead`, `smart-ops-promo-coupons-sync`, `social-publish-worker`, `zernio-provision-flow`, `lia-assign`, `cognitive-lead-analysis` and `sentinela-email-report` live in the AGENTS.md of each of those function directories.
- Evolution GO `/group/create` receives participants as full `55DDDNUMBER@s.whatsapp.net` JIDs; bare digits make WhatsApp drop the request ("info query timed out") and no group is created.
- Commercial campaign forms are `sdr_captacao` forms flagged `smartops_forms.is_commercial_campaign` (legacy: name prefix `# - CAMPANHA COMERCIAL -`; same standard flow), so renaming never turns off buttons, group redirect or exact-name origin; lia-capture asks the form's capture buttons after identity and before ingest, validates the choice server-side, sends it as the CRM product of interest with the exact form name as origin, and auto-opens the success_redirect_url group; keeps campaign CRM routing identical to SDR forms.
- Commercial campaign forms link their promotional table via `smartops_forms.promotional_table_id`; lia-capture uses the linked table name as campaign display name and stores the link on the interest timeline entry, so the table remains the single campaign identity. lia-capture sends the campaign's event (form `event_id`, else the linked table's `event_id`) as `event_id` on ingest so `fn_event_lead_stats` counts its submissions and wins on the event card.

- Brand identity (palette, fonts, logos, references, image style) lives in the single-row `brand_identity_settings` table edited in Configurações do Sistema → Padrão da marca (admin-only writes); AI image generators prepend `brandPromptBlock` from `supabase/functions/_shared/brand-identity.ts` instead of hardcoding hex colors, so one edit updates every generated image.
- Form field copies (duplicate RPC, standard flow, KOL referral forms via `_shared/clone-form-fields.ts`) give every question a new ID and remap `conditions.show_if.rules[].field_id` to the copy; rules pointing at another form's questions never match an answer and break the WhatsApp simulator question order.
- Every non-promotional event gets three forms from the `smartops_events` insert trigger: distribution, a lead form copied from `cipro-cadastro-de-leads` (`fn_clone_lead_form_for_event`) and a KOL interest form (`kol_expansao`) copied from the inactive `kol-expansao-modelo` template with remapped condition IDs; ingest routes `kol_expansao` to `kol-expansao-crm-sync` (rules in `_shared/kol-expansion.ts`), outside the Vendas Golden Rule, so editing a template changes only future events.
- lia-capture (WhatsApp simulator/landing chat) forwards `form_purpose` `kol_expansao` like `distribuicao`, skips the sales-deal "Resumo do Lead" note for it, and re-sends all chat answers to `kol-expansao-crm-sync` (service key) when the last question is answered; otherwise chat leads of KOL forms fell into lia-assign and the Funil de vendas.
- `wa-field-capture` (Captura WhatsApp): inbound Zernio messages from active team phones (`fn_team_member_by_phone`, trigger `trg_dispatch_field_capture`) open a `field_capture_sessions` row only with the exact start word AUTO (other team messages stay normal inbox) and build it until the exact word FIM (no reminder, no auto-close); FIM waits for media still being read, then replies a summary (name/phone/e-mail) and the lead is only created after the seller answers 4 (1/2/3 edit, stored in `confirm_edits`, which override AI reading) so misread cards never reach the CRM; type 1 LEAD/2 KOL/3 OPORTUNIDADE picks the event form (`feira_evento` with the sender as event consultant, `kol_expansao`, or a per-event inactive `oportunidade_evento` system form routed by ingest to `kol-expansao-crm-sync` → funil 109841, Beatriz), so captures reuse the official ingest, origins and event counts; after a WhatsApp-confirmed capture with a phone, it also sends a native WhatsApp contact card (Zernio `contacts`) built from the confirmed data so the seller can tap Salvar contato. Capture phones are stored and sent to ingest as one E.164 number via `_shared/phone-country.ts` (explicit `+`, the lead's country, then the event `country`, else Brazil only with a real DDD; lia-capture applies the same helper with the form's event country); extra card numbers stay separate in `outros_telefones`, because bare US numbers otherwise become fake +7/+55 phones and concatenated numbers.
