- zernio-wa-broadcast `test` sends to up to 5 typed numbers (or the fixed test lead) without creating a campaign; variables use the lead matched by normalized phone, else fallbacks, so the screen stays open and nothing reaches the audience.
- `zernio-wa-broadcast` reads the template header from the approved Meta template server-side and refuses media-header sends without the campaign's own https media (sent as header component + `headerMedia`), so the approved sample is never delivered; `perHour` splits the TOTAL audience into hourly slots (`plan.ts`, then one broadcast per variable combination inside each slot, scheduled via `/broadcasts/{id}/schedule`), because per-variable-group batching would exceed the hourly limit.
- `zernio-wa-broadcast` reads header/buttons/footer from the APPROVED template, requires the campaign's own header image (JPG/PNG ≤5 MB, uploaded to `wa-media/whatsapp/{campaign_id}/`) and deletes the draft and aborts when Zernio's broadcast does not echo that `headerMedia`; per-hour blocks and schedules are pushed into the 07:30–19:00 São Paulo window, quick-reply buttons with a link store label/link/reply text/form in `campaigns.metadata.button_replies` and one `wa_button_reply_rules` row per send (tests included, keyed by broadcast ids), and `action: test` sends only to the fixed test lead without creating a campaign; Zernio otherwise falls back to the approved sample image.
- `zernio-wa-broadcast` `perDay` caps sends per rolling 24 h from each period's first slot (Meta's unique-contact tier), mirrored in `src/lib/waBroadcastSchedule.ts` (tests on both sides); literal variables accept `{campo}` system-field tokens filled per lead by `fillTokens`, and the estimated cost (`costPerMessage` × recipients) is stored in `campaigns.metadata`/session results, so the screen's batch list and cost match what is actually scheduled.
- zernio-wa-broadcast maps the first name variable (`primeiro_nome`/`nome`) to Zernio's per-recipient `field: "name"`, so distinct names never split a campaign (400-broadcast cap). Zernio copies the contact name when a recipient is added, lists at most 200 per page and its `skip` pagination repeats/skips rows, so every broadcast holds ≤200 recipients: bulk-create contacts with names, add phones to a never-sent draft, read one page, PATCH wrong names, then add the same contactIds to the real broadcast and re-check (group cancelled on mismatch). The Zernio client waits on Retry-After/low X-RateLimit-Remaining (600 req/min) instead of failing groups.
- zernio-wa-broadcast `send` attempts that fail before their campaign session exists (validation, template, image or Zernio errors; not 401/403/409) are recorded as `campaign_sessions` status `failed` with `results.error` (`attempts.ts`); broadcasts created directly in the Zernio panel never pass through the system and do not appear in campaign history.
- Official WhatsApp "SAIR" replies are logged to lead_activity_log as `whatsapp_oficial_sair` by the `trg_log_wa_official_sair` trigger on whatsapp_inbox (zernio inbound, text reduced to letters equals "sair", one row per inbox message); it never sets opt-out flags, so zernio-whatsapp-inbox stays ingest-only. The same trigger upserts the canonical lead into `wa_official_sair_leads` (admin-read only), which the Campanhas audience filter joins through PostgREST embedding (`src/lib/waSairFilter.ts`; WhatsApp Oficial/SMS, whose audiences resolve in the browser), so exclusion works for any list size without touching lia_attendances.
- Campaign history reads WhatsApp Oficial numbers live from Zernio through zernio-wa-broadcast `status` (summed over every broadcast and mirrored into `campaigns`; per-lead send log gets the slot time as sent_at and Meta refusals as failed with reason, since conversion counts sent_at) and WhatsApp group campaigns from wa_message_queue via `fn_wa_group_campaign_stats`; `campaigns` rows mirrored by a session (linked id, or same SMS name/channel within minutes) are hidden, so totals are real and nothing appears twice (rules in src/lib/campaignHistory.ts).
- WhatsApp Oficial per-lead status (sent/delivered/read/Meta refusal) comes from `zernio-wa-recipient-sync` (hourly cron, 10-min debounce in cron_state, read-only on Zernio) through the service-only `fn_wa_official_apply_recipients`, matched by session + broadcast + phone; `opened_at` means "lido" for these rows, and `fn_lead_timeline_unified` labels them by provider so they never show as SMS.
- The "Histórico WhatsApp API" tab reads send status live from Zernio (`status`, which also stores the approved template's `template_buttons` order) and per-lead clicks/SAIR from the invoker RPCs `fn_wa_official_campaign_recipients`/`_engagement`: a click belongs to the campaign whose message it quotes (send-log wamid, else the echoed broadcastId), SAIR to the latest official send before it, real cost = delivered × the campaign's `cost_per_message` (`src/lib/waOfficialHistory.ts`); Zernio returns no billed amount.
